御剑 · 剑修战斗系统 —— 战斗设计说明

一份数据驱动的第三人称剑术战斗系统。没有动画文件：姿态由解剖学自由度 + 手部 IK 定义，
帧数据、解剖约束、平衡规则全部写在 Data/*.json，代码里不许有第二套数值。
本文按战斗策划的三块职责组织，每一条都给出为什么这么定和怎么验证。

〇 · 一句话说清这个系统的赌注

把"手感"从形容词变成可执行的断言。

"动作符合人体动作学""打击感好""流畅" —— 这三句话在评审里是没法反驳也没法通过的。

所以这个工程做的第一件事，是把它们逐条翻译成能在命令行跑出红绿的检查：

说法断言工具
符合人体动作学逐帧逐骨比对 ROM；肩肱节律；膝-胫骨自转门；双手可达性Tools/audit.mjs
流畅相位边界时间弯曲导数为 0；jerk 无孤立尖峰Tools/smoothness.mjs
有转身、不是只用手臂骨盆偏航 ≥35°；髋肩分离符号必须变号且两侧 ≥25°Tools/limbcheck.mjs
平衡剑意收支闭合；停顿分级；取消窗口结构；无严格劣势招Tools/balance.mjs

这是整个作品最想表达的东西：策划的产出不该是"我觉得手感更好了"，

而是一组改了就会红的规则。红了就知道坏在哪，绿了才有资格说"这版没问题"。

一 · 设计战斗机制（职责 1）

1.1 架构：帧数据是契约，不是参数表

一招 = frames + phases + keys + hit + cancel + skill。

phases（起手/斩击/命中/收势）不只是提示文字，它驱动插值：

每段的缓动被翻译成"端点速度"，再以相位边界为节点建一条 C1 连续的单调 Hermite。

为什么不是每段各自缓动：那样段与段之间速度不连续。实测 a3 的边界跳变达峰值的 69.7%，

画面上是"预备完停住、然后弹出去"。改成共享端点斜率后，10/10 招的边界导数跳变 = 0.0000（解析可验证）。

1.2 剑意的模型是开关，不是蓝条

来源：a1 25 + a2 25 + a3 50 = 一轮地面三连正好 100（满）
消耗：takeoffCost = 0

takeoffCost = 0 是有意的，不是漏填。 攒满才能起飞；起飞后不清零，

御剑态的招式由"是否在御剑态"把关，而不是再扣一次资源。

为什么不做成蓝条：蓝条会让玩家不敢用。资源被扣空意味着"内容被藏起来"，

玩家会退回最省的打法。做成开关之后，玩家的努力换来的是一段时间的战斗形态变化

（地面剑术 → 御剑飞行 + 召唤剑气 + 巨剑 + 处决），这是内容，不是消耗品。

校验：一轮三连的产出必须正好等于上限。多了是溢出浪费（玩家觉得白打），

少了就永远飞不起来（玩家觉得系统坏了）。

1.3 取消窗口：结构规则，不是手感数值

统一规则：必须打完自己的判定帧才能取消（cancel.from = hit.active[1] + 1）。

招式判定帧可取消占比
a1 斜斩[18,20]2181%
a2 反撩[9,11]1267%
a3 上撩[13,16]1765%
pierce 贯穿[4,18]1990%
great_cleave[60,64]6568%

为什么不用"越重取消越晚"：我第一版写了这条规则，它把 a1 判红了 —— 而 a1 是连段起手，

它本来就应该最好取消，否则连段接不起来。取消窗口的形态由"连段位置"决定，不由伤害决定。

（这条自我纠错写在这里，因为规则本身也是设计产物，也会错。）

1.4 空挥惩罚

cancel.missExtraRecoveryFrames = 2（8 个招式）。

来源：卡普空官方 SF6 帧数据 —— *"2 frames of recovery added when the attack misses"*。

没有它，玩家会无脑空挥去刷取消窗口，把"出招要付代价"这件事抹掉。

1.5 命中停顿按重量分级

分级区间招式
轻2~4 帧a1 (4)、a2 (4)
重6~10 帧a3 (6)、pierce (6)
大招12~18 帧great_cleave (14)、execution (14)

所有攻击同一个停顿值 = 把战斗层次拍平 —— 轻击和巨剑劈下来手感一样重，

玩家就读不出自己拿了什么牌。校验器断言停顿随伤害单调不降。

例外（写进规则，不是漏掉）：伤害由飞出去的剑气自己结算的招式（ride_a1/a2、qi_swords）

不该有停顿 —— 玩家正在御剑飞行，被自己的弹体打断动作是错的。

二 · 扩展战斗玩法（职责 2）

2.1 战斗循环

地面三连（攒剑意）→ 满 100 → 空格御剑起飞（形态切换，不可打断）
                                    ↓
              御剑态：F 贯穿冲刺 / 左键 剑气 / E 六剑齐发 / Q 巨剑竖劈 / X 斩杀

形态切换是这套玩法的支点：地面是"接近、起手、攒"，御剑是"机动、爆发、处决"。

玩家在一场战斗里会经历两次形态转换，每次转换都改变可用的动作集和移动方式。

2.2 十招各有明确职责，没有两个是同质的

招式帧伤害职责
a1 斜斩·右袈裟2610起手段。可取消最早，负责开启连段
a2 反撩·左逆袈裟1812节奏段。最短的一招，用来调连段节拍
a3 上撩·起势2616收尾段 + 起飞引信。伤害最高、顿最重
takeoff 御剑·踏剑起720形态切换，不可打断 —— 它是仪式，不是攻击
pierce 御剑穿身2118机动位移 + 贯穿。判定窗 [4,18] 覆盖整个冲刺
ride_a1 御剑·剑气2014单发远程，验证飞行手感
ride_a2 御剑·连环剑气2633三连发，节奏输出
qi_swords 凝剑·六剑齐发6042扇形控场
great_cleave 巨剑竖劈9645全场最重一击。36 帧预告 + 巨剑下落轨迹本身是预警
execution 斩杀·撕裂黑暗120999处决技，八拍演出

2.3 一条具体的设计判断：依序发射优于齐射

ride_a2 的三道剑气间隔 3 帧（0.05s）依序发出，不是同时。

为什么：齐射是一次性事件，玩家只看到一个瞬间；依序发射给了一个节拍器 ——

玩家能预判、能配合位移、能读节奏。可读性高一个量级，代价只是 6 帧。

同理 qi_swords 的 6 把剑是扇形排列且第一把先出现：6 是一个被验证过的可数数量，

第一把先出会带着玩家的视线走。

2.4 预警的设计判断：不做区域预警

great_cleave 用 lockMode: lockCurrentPosition（锁定当前位置下落），而不是区域预警圈。

为什么：区域预警会把"躲"变成"看图标"。而下落轨迹本身就是预告 ——

玩家抬头看到巨剑下来了，这个信息是空间性的，不是 UI 性的。打空会挫败，

但锁定落点让"打空"变成玩家的判断失误而非系统的欺骗。

三 · 提升战斗表现（职责 3）

3.1 把"粗糙"拆成两个可修的原因

程序化动作看起来廉价，只有两个签名特征：

特征原因修法结果
全身像一块刚体同时移动所有通道在同一个 t 求值重叠动作：按动力链深度滞后φ = 0.010~0.065（段长比例）
末端没有甩出去的余韵单调 Hermite 在数学上禁止过冲—— 尚未做（见 §5）

重叠动作的纪律：滞后必须按段长的百分比，不能按绝对帧数。

研究报告里"每跳滞后 1~2 帧"是 24fps 慢速动画的经验；6 跳链按绝对帧数累计 375~500ms，

而一次挥砍的打击段只有 50~133ms —— 剑尖永远到不了打击姿态，动作直接坏掉。

按比例之后，5 帧的打击段自动只滞后零点几帧，40 帧的预备段自动滞后几帧。

IK 目标必须一起滞后：手的目标点也是通道。只滞后上半身却把手钉在原来的时刻，

IK 会把滞后拉回去，等于白做。

3.2 动力链：躯干不是"转身"，是拧紧后反超

实测 a1：

帧髋线肩线分离
0 站架76.0°69.3°−6.7°
7 起手顶点48.0°80.8°+32.8°
18 命中114.0°82.4°−31.6°

骨盆转了 66°，而肩线只走了 2° —— 躯干在底下拧紧、肩线被留在后面，命中时反超 31.6°。

这条被解剖约束强制：trunk_rotation_budget 要求骨盆+三段脊柱的旋转总和 ∈ ±75°。

所以正确结构必然是反向的：骨盆 +42、三段脊柱合计 −29 → 净旋转只 13°（解剖安全），

但肩线相对髋线分离 29°（力量感）。解剖约束和"有力"在这里是同一件事。

判据要跟动作类型走：横斩看水平面拧紧，竖劈/起飞/突刺看矢状面屈伸

（pelvisTilt + 三段 flexion）。我第一版只用水平判据，于是 great_cleave 报了假红。

招式类型幅度
a1 / a2 / a3水平拧紧66° / 28° / 66°
takeoff矢状屈伸92°（深蹲→伸展）
great_cleave矢状屈伸124°（指天 −34° → 下劈 +90°）
execution矢状屈伸87°（收紧 +48° → 撕裂 −39°）

3.3 一帧数据的说服力：上撩的手够不到

给 a3 补躯干时，后仰从 −28° 加到 −46°，肩关节往后移约 14cm，

而手的目标点是角色根空间的绝对坐标 —— 审计报「目标超出臂长 8.6cm」。

这说明躯干和手部 IK 是机械耦合的：不能"先改躯干再看结果"。

最终建成 Tools/fit-ik.mjs：用审计量出来的超限量驱动，沿"肩→手"方向把距离缩回来，

方向不变 → 手臂指向不变。

（它第一版用闭式解 reach = dist / reachRatio，被实测证伪：自己算 0.1cm、审计报 8.6cm。

两套口径对不上时以审计器为准 —— 判红绿的是它。）

3.4 特效层：颜色和触发区间都在数据里

Data/effects.json 是唯一真相，渲染器和 Unity 侧都读它，代码里不硬编码色值：

core #ffffff   hot #c8f6ff   qi #4fd8ff   deep #1b7fc4   jade #5cf0be   void #03101a

配色决定：参考片是火焰红橙，这里换成剑气的蓝白青绿。

抄它的结构与节拍，不抄它的色。

四个特效层 + 一条绘制顺序纪律：

漩涡 → 径向爆发 → 全黑 → 撕裂光缝 → 闪白

顺序不能挪：黑场必须盖住角色，而光缝必须盖住黑场 ——

这样"由一点变一竖把黑暗撕开"才成立；顺序反了就变成"光缝被黑暗盖住"，什么都看不见。

剑气月牙的出生帧不手排：取剑尖速度的局部极大值（>7 m/s、间隔 ≥6 帧）。

剑尖什么时候最快，剑气就什么时候离刀 —— 这是同一件事。

辉光（bloom）已进 Unity：Assets/Shaders/QiBloom.shader + QiBloom.cs，

Built-in RP 的 OnRenderImage 里三次 Blit（亮度阈值 → 可分离高斯 → 加色合成）。

零第三方依赖。失败必须降级为直通而不是抛异常 —— 这个工程里 Shader.Find 返回过 null，

new Material(null) 抛异常把整条 BuildCamera 打断，表现是演示"动不了"。

四 · 平衡是可断言的（职责 1 的"维护"）

Tools/balance.mjs 查 7 条，每条对应一个真实会毁掉体验的失败模式：

1. 剑意收支闭合 —— 一轮三连产出 == 上限

2. 命中停顿分级 —— 每个"自己命中"的招式都落在重量区间内

3. 停顿随伤害单调不降 —— 不能出现更轻的招顿得更久

4. 取消窗口结构 —— 不早于判定帧结束

5. 无严格劣势招 —— 没有一招在伤害效益与削韧效益上被同时压制

6. 削韧/伤害比值 ∈ [1.1, 1.5] —— 保证削韧不退化成"伤害的别名"

7. 可调数值只出现在 Data/ —— 代码里不许有第二套

这一轮校验器找出的东西（含我自己写错的规则）

判定条目结论
真pierce / execution 缺停顿已修：6 / 14
真great_cleave 顿 10已修：14（全场最重一击必须压过所有重击）
真取消窗口不一致已修：统一为"判定帧结束后"
真takeoffCost 写在 C# 里未修，违反纪律，见 §5
假ride_a1/a2、qi_swords 缺停顿规则错：伤害由飞出的剑气结算，不该停顿
假qi_swords 被 execution 压制规则错：处决技不参与可重复招式的效益比较
假取消窗口随伤害单调规则错：应由连段位置决定

把这三条写进文档，是因为它们比"全绿"更有信息量：

校验器的价值不是通过，而是逼人把"真问题"和"我拍脑袋定的规则"分开。

五 · 诚实的边界（还没做的）

1. 末端过冲（follow-through）没做。 这是"机械感"的根因：

单调 Hermite 在数学上禁止过冲，而甩出去的余韵本质就是受控过冲。

研究报告把它排第一（提升 5 星 / 成本 2 星），做法是给腕/肘/剑尖叠一层二阶阻尼弹簧

（ζ=0.45~0.60 → 过冲 9.5~20.5%，剑尖只用 3~7% 否则会甩飞）。

2. 能量羽翼、地面法阵、撕裂屏幕特效只在预览渲染里，Unity 侧还没实现（辉光已做）。

3. takeoffCost 等可调数值仍在 C# 里（SwordQi.cs），应移到 Data/balance.json 由生成器注入。

4. 手部管线：腕角由 blade.dir 反推，而它要求的轴向旋转超出腕的 ±25°；

解剖上该由前臂旋前（LowerArm.pronation [-85,90]，数据里早有、解算器从没用过）承担。

5. IK 肘部分支不稳定：审计里约 97 条错误来自解算器在多个极小值之间跳

（77~130°/帧，人体不可能），不是真实动作问题，但会污染角速度读数。

6. JS 与 C# 无数值一致性测试：审计跑的是 Tools/lib/rig.mjs（PoseSolver.cs 的镜像），

本轮已经抓到过一次"审计测新曲线、运行时跑旧曲线"的静默分歧。

两套实现的等价性需要一个自检用例来保证。

六 · 怎么验证（可复现）

node Tools/audit.mjs --moves      # 人体动作学：ROM / 耦合 / 动力学
node Tools/smoothness.mjs         # 流畅度：相位边界导数、jerk
node Tools/limbcheck.mjs          # 肢体链条：骨盆偏航、髋肩分离、屈伸
node Tools/balance.mjs            # 平衡：7 条不变量
node Tools/fit-ik.mjs             # 手部可达性配平（--apply 写入）
node Tools/render.mjs             # 渲染成可交互的预览页（Docs/预览-战斗系统.html）

# 真编译（必须关闭编辑器，否则会"假绿"）
powershell -File Tools/unity-compile.ps1

Tools/lib/sampler.mjs 是审计器与渲染器共用的插值实现 ——

两份拷贝一旦漂移，就会出现"审计说没问题、画面上却在抖"这种最难查的情况。

任何插值规则的改动都必须同时改这里和 Assets/Scripts/Motion/PoseMixer.cs。
